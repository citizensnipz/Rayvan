# Native checkpoint and token formats

## Checkpoint and configuration versions

A checkpoint is a directory, not one opaque blob:

```text
checkpoint/
  manifest.rayvan
  model.rvcfg
  model.pt
  optimizer.pt       # training checkpoints only
  rng.pt             # CPU/CUDA and sampler RNG states when supplied
```

`manifest.rayvan` and `model.rvcfg` are UTF-8, line-oriented `key=value` files. The checkpoint manifest remains `rayvan-emc-checkpoint-v1`; newly saved model configurations use `rayvan-emc-config-v4`. The reader still accepts v1-v3 configurations and supplies historical defaults for fields introduced later; v1/v2 are legacy-Nexus models. V3 introduced the routing-free N1 mode, shared GQA/RoPE, routing granularity, and predecessor norm-gate fields. V4 adds the learned need embedding and competence-basin geometry, utility, uncertainty, novelty, exploration, and replacement parameters. The predecessor gate fields remain readable for compatibility but are not used by current competence-basin routing. Unknown fields may be ignored by later readers; required fields must be present. Population order is a comma-separated list of `gpt`, `ssm`, `recurrent`, and `delta`.

`model.pt`, `optimizer.pt`, and `rng.pt` use LibTorch `OutputArchive` serialization. The manifest records format version, file names, active top-K, step, processed tokens, validation/best loss, seed, and precision. `rng.pt` stores CPU/global, CUDA-default, training-sampler, and evaluation-sampler generator states so stochastic Bernoulli/exploration routing resumes reproducibly. The model config records every architecture-defining native field, including ordered N1 population, depth, family dimensions, Delta heads/feed-forward width, chunking, Delta scratch limit, legacy top-K, tying, and all competence-basin settings. Basin tensors, running utility, cumulative routing counters, and need-projection parameters are registered model state in `model.pt`.

For tied embeddings, `model.pt` stores the token embedding matrix once. `output_projection.weight` is reconstructed as an alias from configuration and is intentionally absent as a second archive entry.

Saves write temporary files and rename them into place. The manifest is finalized last. A directory with a missing manifest is incomplete.

Evaluation loading reads `manifest.rayvan`, `model.rvcfg`, and `model.pt` only. It never opens or deserializes `optimizer.pt` or `rng.pt`; optimizer tensors therefore cannot create an evaluation-time CUDA peak. Training resume explicitly loads the separate optimizer/RNG archives after model validation. Model loading rejects a stored N1 mode that differs from the constructed model. `active_top_k` remains in the v1 checkpoint manifest for compatibility but is restored only for legacy-Nexus models.

LibTorch archives are stable within PyTorch's supported serialization compatibility, but are not claimed as a language-neutral long-term format. The text manifest is the compatibility gate. A future incompatible tensor archive must increment the checkpoint format.

## Python weight conversion

`cpp/python/export_reference.py` exports Python `state_dict` entries as registered buffers in a TorchScript tensor carrier. Dots in state names are encoded as `__DOT__`; the C++ importer decodes them, validates every native parameter shape, and copies values into the already-constructed architecture. Cached masks are regenerated by model construction. The deterministic fixture includes GPT, SSM, recurrent, and Delta N1 nodes. The conversion path is:

```powershell
$env:PYTHONPATH = "emc"
python cpp/python/export_reference.py cpp/tests/fixtures/reference
```

For a production Python checkpoint, use the same carrier convention with the checkpoint's `model_state`; its model configuration must be translated into `model.rvcfg`. The C++ runtime uses `torch::jit::load` for this one-time import and does not embed Python.

After import, call native `save_checkpoint` to produce a native checkpoint directory. The original Python `.pt` optimizer payload is deliberately not loaded during native evaluation. Optimizer migration requires an explicit field-by-field converter because Python pickled optimizer containers are not a stable C++ runtime format.

## Pretokenized dataset v1

`.rvtok` is little-endian:

| field | type |
|---|---|
| magic | 8 bytes, `RVTOKEN1` |
| version | `uint32`, 1 |
| token count | `uint64` |
| fingerprint | `uint64` |
| split-ID byte length | `uint32` |
| split ID | UTF-8 bytes |
| tokens | token count × `int32` |

The fingerprint is FNV-1a-64 over `split_id`, one zero separator byte, and every token encoded as four little-endian bytes. Both Python and C++ exporters can reproduce it. Loading verifies the count and fingerprint before sampling. The split ID should identify the exact corpus revision and train/validation split, not merely the word `train`.
